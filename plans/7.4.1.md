# Plan: 7.4.1

Target: 7.4.1 (patch), with two fixes in one release and one PR each.

- **Part A: blog post drafts can be edited after `create_blog_post`.** In 7.4.0 a draft can be created but not changed: `add_attachment` returns 404 and `update_blog_post` returns 400.
- **Part B: duplicate global installs are made visible.** `get_version`, `upgrade` and `status` list the installed copies, so an upgrade that hit the wrong copy is no longer silent.

The parts touch different code (A: `confluence-client.ts` and the blog/attachment tool handlers; B: a new module plus `get_version`, `upgrade` and `status`). They share only `CHANGELOG.md` and `src/server/index.ts`, in different handlers. Each PR is small enough to review in one sitting, and either can ship without the other. A goes first because it blocks a real workflow; B is a usability fix.

## Part A: drafts cannot be changed after `create_blog_post`

### Problem

`create_blog_post` creates a draft by default (`publish` is opt-in, because publishing emails the space's watchers). The intended flow for a post with images is:

1. create the draft;
2. upload the images;
3. set the body that references them;
4. read it back and let the author check the rendered draft;
5. publish.

In 7.4.0 only step 1 works. Reproduced on Confluence Cloud on 2026-10-15, with a fresh draft in a personal space, no `spaces` allowlist:

| Step | Call | Result |
|---|---|---|
| 1 | `create_blog_post` (no `publish`) | `{"kind":"written","page_id":"<draft-id>","new_version":1}`; `get_page` shows a draft |
| 2 | `add_attachment` on `<draft-id>` | `Error: Resource not found. Confluence may return 'not found' when a token lacks permission…` |
| 3 | `update_blog_post`, `version: 1`, new body | `400 BAD_REQUEST: DRAFT blogposts do not support multiple versions. Expected version: [1]. Provided version: [2]` |

So a post with images can't be prepared as a draft. The only workaround is to publish first and attach afterwards, which emails watchers about an incomplete post.

### Cause

**A1, attachments.** Every v1 attachment call names the container by id only:

- `uploadAttachment` (`POST /content/{id}/child/attachment`);
- `getAttachments` and `findAttachmentByName` (`GET /content/{id}/child/attachment`);
- `uploadAttachmentVersion` (`POST /content/{id}/child/attachment/{attId}/data`).

The v1 API looks the container up as `current` unless `status=draft` is given. A never-published draft is therefore "not found", even though the token can read and write it. That is also why the error text, which blames token permissions, is misleading here.

The blog write tests don't catch this. The `add_attachment` case in `blog-post-write.integration.test.ts` uses the published `BLOG_ID`, and the mock serves `/child/attachment` for any id.

**A2, draft updates.** `_rawUpdateContent` always sends `version.number = opts.version + 1`. Confluence keeps no history for a draft blog post: a `PUT /blogposts/{id}` that leaves the post `draft` must send the version it has (1). The test asserts the wrong value: `blog-post-write.integration.test.ts:828` expects `{ status: "draft", version: { number: 2 } }`, and the mock accepts any number.

**A3, publishing a draft: not yet verified.** Publishing (`publish: true`, test at line 865) also sends `version: 2`. If Confluence expects 1 when a never-published draft becomes `current`, publishing fails the same way. That failure would come after the publish confirmation was answered, so the user would approve a publish that then doesn't happen. This must be settled live before the fix is written; see Step A0.

**A4, other side writes on a draft: unknown.** Labels (`POST/DELETE /content/{id}/label`) and content state (`PUT /content/{id}/state`) are v1 calls without a status. The v2 footer comment (`POST /footer-comments` with `blogPostId`) has no status either. The mocked test at line 425 shows `add_label` on a draft writes to `/content/{id}/label`, but the mock accepts it for any id, so nothing proves Confluence does.

### Step A0: live probe, before any code

The fix depends on Confluence behaviour that isn't documented clearly, so it starts with a probe against a real tenant. Use a scratch draft in a personal space and record each answer in the PR description.

| # | Request on a never-published draft | Question |
|---|---|---|
| P1 | `POST /content/{id}/child/attachment?status=draft` | Does the upload succeed? Does the file then show in the draft editor? |
| P2 | `GET /content/{id}/child/attachment?status=draft` (with and without `filename`) | Does it list the file from P1? |
| P3 | `POST /content/{id}/child/attachment/{attId}/data?status=draft` | Does it add a version? |
| P4 | P1 and P2 **without** `status` | Confirm the 404 (the cause above). |
| P5 | `?status=draft` on a **published** post or page | Ignored, or a 404? This decides whether the parameter can be sent only when needed or whether it must be computed exactly. |
| P6 | `PUT /blogposts/{id}`, `status: draft`, `version: 1` | Succeeds, and the version stays at 1? |
| P7 | `PUT /blogposts/{id}`, `status: current`, `version: 1` and then `version: 2`, on two separate scratch drafts | Which one publishes? Is the published post at version 1 or 2 afterwards? |
| P8 | label add/remove, content state set, footer comment, each on a draft | Works as-is, works with `?status=draft`, or not supported? |
| P9 | the draft's `version.createdAt` before and after a P6 update | Does anything in the draft's metadata change on each save? (See "Concurrency" below.) |

How the probe runs:

- The probe goes through the product's own code path, so the agent never handles the API token. It is a small script under `scripts/probe/` (not shipped) that imports the built client with the user's profile, or a dev build of the MCP server called over stdio.
- Each probe uses a fresh scratch draft and deletes it afterwards.
- **P7 publishes two posts.** Publishing emails the space's watchers, so it needs the user's go-ahead for the chosen space before it runs, and it should run in a personal space nobody else watches.

**Results (Confluence Cloud, 2026-10-15, a personal space; all scratch posts deleted afterwards):**

| # | Result |
|---|---|
| P1–P3 | With `?status=draft`: the upload, the listing (with and without `filename`) and `/data` all work; `/data` adds version 2. |
| P4 | Without `status`: the upload is a 404 ("No content found with id … and status [current], there is a content object with status : draft"). `/data` without `status` works. |
| P5 | `?status=draft` on a published post: the upload is a 404 and the listing answers 200. So the status must be computed exactly, never always sent. |
| P6 | `PUT` with `status: draft`, `version: 1` works and the draft stays at version 1. `version: 2` is the 400 from the bug report. |
| P7 | Publishing with `version: 1` works and the post is at version 1. With `version: 2`: 400 "Version number must be 1 when publishing a blogpost for the first time". The first edit after publishing is version 2. |
| P8 | Labels work without `status`. Content state needs `?status=draft` (the client sent `status=current`: 404). A v2 footer comment on a draft is a 404: drafts take no comments. |
| P9 | The draft's `version.createdAt` changes on every save, so a stale-read check is possible in a later release. |

Also seen: a plain `GET /blogposts/{id}` answers 200 with `status: draft` for a draft on this tenant, and deleting a draft needs `?draft=true`.

### Design

**A1, a draft-aware container for attachments.**

- `confluence-client.ts` gains `resolveContainerStatus(id): Promise<"current" | "draft">`.
  - It uses the same read order as `resolveContentSpace`: `getContent` (pages, then blog posts), then `getDraftBlogPost` after a 404.
  - It is **not cached**: publishing turns a draft into a current post, and a stale "draft" would break the next attachment call. It costs one or two metadata GETs per attachment tool call.
  - Errors propagate. A failed lookup fails the tool before anything is uploaded.
- `uploadAttachment`, `uploadAttachmentVersion`, `findAttachmentByName` and `getAttachments` take an optional `{ draft?: boolean }`. When it is true they add `status=draft` to the URL. Pages and published posts send exactly the URLs they send today (asserted by a test).
- The tool handlers resolve the status once and pass it down: `add_attachment` (both the plain and the `overwrite` paths) and `get_attachments`.
  - `add_drawio_diagram` / `update_drawio_diagram` already refuse blog posts, so they are unchanged.
  - The other caller of `getAttachments` (`src/server/index.ts:1014`) is reviewed in the PR.
- If P5 shows that `status=draft` is harmless on current content, the lookup could be replaced by always sending it. Even then I would keep the lookup: it keeps page requests byte-identical to 7.4.0 and costs one GET.
- **Error text:** a 404 from an attachment call on a draft, if one still happens, should not blame token permissions. `toolErrorWithContext` for `add_attachment` / `get_attachments` says "blog post <id> is a draft; …" when the container resolved as a draft.

**A2 and A3, version numbers for drafts.**

- `RawUpdateOptions` already carries `status`. `_rawUpdateContent` computes the version it sends from the status it read and the status it writes:

  | Before | After | Version sent |
  |---|---|---|
  | page or `current` post | `current` | `version + 1` (unchanged) |
  | `draft` | `draft` | `version` (stays at 1) |
  | `draft` | `current` | from P7: `version` or `version + 1` |

  So `_rawUpdateContent` needs the current status. `update_blog_post` already has it (`current.status`) and passes it as `fromStatus`.
- The result and the mutation log report the version Confluence returns, not a computed `+1`. A draft edit reports `new_version: 1`, and so does a publish if P7 says so. The "still a draft" text stays.
- **409 and outcome-unknown handling:** the S7 branch ("the page is still at the version the caller sent, yet the PUT got a 409") and the R1 outcome-unknown mark both assume every write bumps the version. For draft-to-draft writes they don't, so both are reviewed against the new table:
  - R1: a re-write of a draft after an unknown outcome is allowed. It is the same overwrite of an unversioned draft, so it is harmless.
  - S7: a 409 on a draft edit is reported as Confluence's text, never as "retry with version N".

**Concurrency on drafts (limitation, documented).** With no version history, the version number can't detect a concurrent edit of a draft: two writers both send version 1. Confluence itself doesn't detect it either. For 7.4.1:

- The `update_blog_post` description and the tools reference say so: on a draft, an update overwrites the current draft body, and the `version` check doesn't protect against a concurrent edit. Read the draft just before updating it.
- The publish confirmation already binds the body that will be published (`computeDiffHash` over `body ?? currentStorage`), so a confirmed publish can't publish content the user didn't approve. A test pins this for drafts.
- If P9 finds a field that changes on every save, a real stale-read check can follow in a later release. It is not part of this patch.

### Tests (Part A)

The mock in `blog-post-write.integration.test.ts` is made as strict as Confluence, so both bugs would have failed CI:

- `/content/{DRAFT_ID}/child/attachment` (POST, GET, `/data`) returns 404 unless `status=draft` is in the query. For `BLOG_ID` and `PAGE_ID` it answers as today, and responds as P5 found when `status=draft` is present.
- `PUT /blogposts/{DRAFT_ID}` with `status: draft` returns Confluence's 400 text unless `version.number === 1`. With `status: current` it accepts only what P7 found.
- Labels, state and comments on `DRAFT_ID` behave as P8 found.

Cases:

- `add_attachment` on a draft: the POST carries `status=draft`; `get_attachments` on the draft lists the file.
- `add_attachment` with `overwrite: true` on a draft: the lookup and the `/data` upload both carry `status=draft`.
- `add_attachment` / `get_attachments` on a page and on a published post: no `status` parameter. The URLs are byte-identical to 7.4.0.
- The status lookup failing (5xx): no upload is sent, and the error is surfaced.
- `update_blog_post` on a draft without `publish`: the PUT has `version.number: 1`; the result says `new_version: 1` and "still a draft". This replaces the assertion at line 828.
- Publishing a draft: the PUT version matches P7, and the result reports the version Confluence returned. This replaces the assertion at line 865.
- Editing a published post: still `version + 1`, unchanged.
- Publish token on a draft: a token minted, then the draft body changed (still version 1), then the token replayed with no `body` → refused (diff hash mismatch).
- **Mutation check:** revert each fix in turn (drop `status=draft`; restore `+1` for drafts) and confirm the matching tests fail.

### Live acceptance (Part A)

On a fresh draft in a scratch personal space, using a build of the branch:

1. `add_attachment` succeeds and `get_attachments` lists the file.
2. `update_blog_post` with `version: 1` and a body referencing the image succeeds. `get_page` shows it is still a draft, still at version 1, with the image rendered in the draft editor.
3. `add_attachment` with `overwrite: true` replaces the file.
4. `update_blog_post` with `publish: true`, once confirmed, publishes it. The result's version matches what `get_page` shows. This step publishes, so it needs the user's go-ahead for the space first.
5. Delete the scratch post.

## Part B: make duplicate global installs visible

### Problem

A machine can hold two global copies of epimethian-mcp. The usual pair is one under Homebrew's npm and one under nvm's npm, each with its own global prefix. The MCP client starts one copy and the terminal finds the other, and nothing says so:

- `get_version` reports the version of the copy the server runs, and nothing else.
- The update notice says "Run `epimethian-mcp upgrade` in your terminal". The terminal runs whichever copy is first on its PATH. Since 7.4.0, `performUpgrade` replaces the copy that runs it (`globalInstallPrefix(realpath(argv[1]))`). So the documented path upgrades the terminal's copy, and the MCP client keeps starting the old one.
- A manual `npm install -g` has the same problem: it writes to the prefix of the first `npm` on PATH.

The user upgrades, reloads, and `get_version` still shows the old version, with no clue why. This was seen in practice in October 2026: it took two reloads and a manual search of the PATH to find.

The two PATHs really do differ. On macOS an IDE started from the Dock doesn't get the login shell's PATH, so nvm's directories are often missing from the server's environment while they come first in the terminal.

### Design

#### B1. Find the installed copies: `src/shared/installed-copies.ts` (new)

```ts
interface InstalledCopy {
  prefix: string;          // npm global prefix
  packageDir: string;      // packageDirUnder(prefix)
  version: string | null;  // from packageDir/package.json; null if unreadable
  running: boolean;        // holds realpath(process.argv[1])
  pathRank: number | null; // position among PATH hits in this process; null if not on PATH
}
```

- `candidatePrefixes({ env, platform, home })` is pure and returns the prefixes to probe. It draws on:
  - **PATH:** every directory in `env.PATH` holding `epimethian-mcp` (`epimethian-mcp.cmd` on win32). Each hit is resolved with `realpath`, then `globalInstallPrefix`. Hits that are not global installs, such as a source checkout or an npx cache, are skipped.
  - **Well-known prefixes**, probed even when they are not on this process's PATH:
    - POSIX: `/opt/homebrew`, `/usr/local`, `/usr`, `~/.npm-global`, and every `~/.nvm/versions/node/*` (or `$NVM_DIR/versions/node/*`).
    - Windows: `%APPDATA%\npm`.
    - The nvm listing is capped at 64 entries.

  Probing well-known prefixes is the point: the server's PATH is the one most likely to be missing the copy the terminal uses.
- `findInstalledCopies(opts)` is async and takes `env`, `platform`, `home`, `runningScript` and the fs functions as injectable inputs. It:
  - checks each candidate for `packageDir/package.json`;
  - dedupes by `realpath(packageDir)`;
  - reads `version`;
  - marks `running` and `pathRank`.

  It never throws: every fs error leaves that candidate out. It only reads the filesystem, and runs no `npm` or child process.
- `describeCopies(copies, runningVersion)` is pure and returns `null` when there are fewer than two copies. Otherwise it returns a block like this:

  ```
  2 copies of epimethian-mcp are installed:
    v7.4.0  /opt/homebrew/lib/node_modules/@de-otio/epimethian-mcp   ← this server
    v7.2.0  /Users/u/.nvm/versions/node/v22.1.0/lib/node_modules/@de-otio/epimethian-mcp
  An upgrade replaces only the copy it runs from. Keep the copy your MCP
  config's "command" starts, and remove the other:
    npm uninstall -g --prefix /Users/u/.nvm/versions/node/v22.1.0 @de-otio/epimethian-mcp
  ```

  The uninstall command uses `--prefix`, so it works whichever `npm` the user runs it with.
- `runningBinPath(prefix, platform)` returns the bin entry under a prefix: `<prefix>/bin/epimethian-mcp`, or `<prefix>\epimethian-mcp.cmd` on win32.

The search only reads, and touches nothing the user didn't install. It reads tens of directory entries and adds well under 10 ms to server startup.

#### B2. Server: startup and `get_version` (`src/server/index.ts`)

- **Startup:** at server start, call `findInstalledCopies` once in the background, next to the existing `checkForUpdates`, and cache the promise. If `describeCopies` returns a block, print it to stderr once.
- **`get_version`:** awaits the cached promise and appends the block. Its failures are caught the same way the update info's are today, so version reporting never breaks.
- **Update notice:** when two or more copies exist, the notice changes from "Run `epimethian-mcp upgrade` in your terminal" to:

  > Ask your agent to run the `upgrade` tool, or run `"<runningBinPath>" upgrade` in your terminal. A bare `epimethian-mcp upgrade` may upgrade a different copy (see above).

  With a single copy the notice stays as it is.

#### B3. `upgrade`: the MCP tool and the CLI (`src/server/index.ts`, `src/cli/upgrade.ts`)

- **CLI, before installing:** print `Upgrading the copy at <packageDir>.` A terminal user then sees which copy is about to change, before anything is written.
- **Both, after a successful install:** find the copies again and list every copy that is not the running one:

  ```
  Not upgraded: v7.2.0 at /Users/u/.nvm/versions/node/v22.1.0/lib/node_modules/@de-otio/epimethian-mcp
  If your MCP config starts that copy, it still runs v7.2.0. Remove the copy you don't use:
    npm uninstall -g --prefix /Users/u/.nvm/versions/node/v22.1.0 @de-otio/epimethian-mcp
  ```

- **CLI result:** `UpgradeResult` gains `otherCopies?: { packageDir: string; version: string | null }[]`, so tests can assert on it without scraping the output.

#### B4. `epimethian-mcp status` (`src/cli/status.ts`)

Add an "Installed copies" line, or the `describeCopies` block when there are two or more copies. `status` is the command the troubleshooting guide already sends people to.

### Rejected alternatives (Part B)

- **Upgrade every copy found.** It writes into prefixes the user didn't pick, some of which need root (`/usr/local`), and it hides the misconfiguration rather than surfacing it.
- **Uninstall the other copies automatically.** It's destructive, and the server can't know which copy each of the user's MCP configs starts.
- **Parse the MCP client configs to see which copy they start.** There are many clients and config locations (`client-configs.ts` lists them), and it would be fragile. Listing the copies plus "keep the one your config starts" gives the user what they need to decide.
- **Run `npm config get prefix` for each npm found.** It spawns processes and is slower, and the well-known-prefix probe covers the common layouts.

### Tests (Part B)

All of these use temp directories with fake prefixes (`<prefix>/lib/node_modules/@de-otio/epimethian-mcp/package.json`, plus a bin symlink into `dist/cli/index.js`). None touch the real global prefixes.

- **`installed-copies.test.ts`:**
  - two prefixes on PATH → two copies, with the correct versions, `running` and `pathRank`;
  - the same prefix reached via PATH and via the well-known list → one copy (deduped by realpath);
  - a copy only under the fake `~/.nvm/versions/node/*` and not on PATH → found (the GUI-PATH case);
  - an nvm folder with three Node versions, one holding the package → one copy;
  - a missing or unreadable `package.json` → `version: null`, no throw;
  - a source checkout's bin on PATH → ignored;
  - the fs throwing on every call → `[]`, no throw;
  - the win32 bin name and layout, through the `platform` parameter of the pure functions.
- **`describeCopies`:**
  - fewer than two copies → `null`;
  - two copies → the block, with the running one marked;
  - the running copy not a global install (a source checkout) → the global copies are listed and none is marked as running;
  - the uninstall line uses `--prefix` with the right prefix.
- **`get_version`**, with the finder injected or mocked:
  - one copy → no block;
  - two copies → a block;
  - the finder rejecting → output unchanged.

  The update notice has the absolute bin path only when there are two or more copies.
- **`upgrade.test.ts` / `perform-upgrade.test.ts`:**
  - after an install with a second fake prefix present, `otherCopies` lists it;
  - with no second prefix, it is absent;
  - the CLI prints the "Upgrading the copy at" line before any install call.
- **Mutation check:** drop the well-known-prefix probe and confirm the nvm-only test fails. Drop the dedupe and confirm the dedupe test fails.

### Real-machine verification (Part B)

1. `npm run build`.
2. Make a second copy in the scratchpad, not in a real prefix: `npm install -g --prefix <scratch>/prefix @de-otio/epimethian-mcp@7.3.0`.
3. Run `PATH=<scratch>/prefix/bin:$PATH node dist/cli/index.js status`. It should list both copies, with the uninstall line naming `<scratch>/prefix`.
4. Start the built server with that PATH and call `get_version` through an MCP client or a stdio harness. Check the block, and the absolute path in the update notice.
5. Delete the scratch prefix.

### Docs (Part B)

- `doc/user-doc/installation.md`:
  - **Step 3:** make the absolute path (`which epimethian-mcp`) the recommended `command`, and say why: the client and the terminal may see different PATHs. Today it is framed as an IDE-only fallback.
  - **Troubleshooting:** a new entry, "Upgraded, but `get_version` still shows the old version". It covers two copies, `epimethian-mcp status` to list them, and `npm uninstall -g --prefix <prefix> @de-otio/epimethian-mcp` to remove one.
- `README.md`:
  - **MCP Configuration:** one line pointing at the absolute-path advice.
  - **Credential Security:** the upgrade bullet notes that `upgrade` replaces the copy it runs from.
- `doc/user-doc/tools-reference.md`: the `get_version` and `upgrade` entries mention the copies block.
- `CHANGELOG.md`: a 7.4.1 "Fixed" entry, written as user-visible behaviour.

## Order of work

1. **A0:** the live probe (P1 to P9). Get the user's go-ahead for P7, which publishes two scratch posts. Record the answers.
2. **PR A**, branch `fix/blog-draft-edits`:
   - stricter mocks first, so the current code fails them (the red run proves the tests can catch the bugs);
   - then the client and handler changes;
   - then docs and the CHANGELOG;
   - then the live acceptance (the publish step needs the go-ahead again).
3. **PR B**, branch `fix/duplicate-installs` (exists, made from master):
   - B1 and its tests (the pure functions first, then the fs-backed finder);
   - then B2, then B3 and B4;
   - then docs and the CHANGELOG;
   - then the real-machine check.
4. A full test run per PR before it is opened, at most one at a time, with `--maxWorkers=2`. Scoped runs while iterating, for example `npx vitest run src/server/blog-post-write.integration.test.ts --maxWorkers=2`.
5. Draft PRs. After both merge: version bump, CHANGELOG date, tag `v7.4.1`, release, publish (each step confirmed at the time).

Users on 7.4.0 can reach 7.4.1 with the `upgrade` tool: the 7.4.0 integrity check works. Users on 7.3.0 or older still need the one-time manual install that the 7.4.0 notes describe.
